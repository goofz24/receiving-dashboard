1. What you have

A web app that reads stock-receiving data from a Postgres database. It has six pages, in a frosted-glass design with smooth animations:

  • Overview: eight number tiles (deliveries, units, mismatches, overdue lines, open orders, fill rate, damaged units, value received, with trend pills), a weekly bar chart you can switch between 4, 8 and 12 weeks, and a donut chart of value by supplier. Click a supplier in the donut and the bar chart filters to it.
  • Deliveries: every delivery, newest first. Click one to open what was on the truck. Tabs for the last 7 days and deliveries with problems, a search box, and Copy as CSV.
  • Purchase orders: every order line with its status (overdue, awaiting, short, over, complete), how late it is, and a progress bar of received vs. ordered.
  • Suppliers: one card per supplier with fill rate, on-time %, value received, a 12-week sparkline and its problem lines.
  • Mismatches: a review queue of short, over and damaged lines. Each card has Copy follow-up, which writes the email to the supplier for you (the app never sends anything itself).
  • Ask AI (optional): type a question in plain English, Claude writes one SQL query, you see the query, and it runs as a user that can only read.

Every card has a </> button that shows the exact query behind it, and the button at the top right lists all of them. That's the point of the project: an interviewer can open any number and you can explain where it came from. Press Ctrl K anywhere to search pages, suppliers, orders and products.

Why the animations are smooth

Every animation moves things with transform, opacity or SVG strokes. The browser can run those on the graphics card at the screen's full refresh rate (60, 120 or 144 times a second) without redrawing the page. Numbers count up with requestAnimationFrame, which also runs once per screen refresh. Bars use a CSS animation the first time and a CSS transition when you filter, so they glide to the new height. If a visitor has "reduce motion" turned on in their system settings, the animations switch off.

4. The database, explained

{{DIAGRAM}}

Six tables live in their own schema called receiving (a schema is a folder for tables). On Supabase, only the public schema is exposed to the internet API by default, so keeping our tables in receiving keeps them off it.

Why split the data into six tables?

Think about the paperwork you already handle at work:

  • suppliers and products: the master lists. A supplier's name is stored once. If it changes, you change one row, not hundreds.
  • purchase_orders and po_lines: the order header (who, when ordered, when expected) and its lines (which product, how many, at what price). One order has many lines, so they can't be one table without repeating the header on every line.
  • receipts and receipt_lines: what actually arrived. A delivery is its own thing because one order can come in two trucks (a split shipment). Each receipt line says how many of one order line were counted on that truck, and how many were damaged.

This is called normalization: each fact is stored once, in the table where it belongs, and tables point at each other with IDs.

Words you should know

Primary keyThe unique ID of a row, like po_id. Postgres numbers them automatically (generated always as identity).
Foreign keyA column that points to another table's primary key, like po_lines.po_id → purchase_orders.po_id. Postgres won't let you add a line to an order that doesn't exist.
Check constraintA rule on a column, like qty_ordered > 0 or "damaged can't be more than received". Bad data is rejected at the door.
IndexA lookup shortcut on columns we search or join on often, like receipts.received_on.
ViewA saved query you can select from like a table. po_line_status is one.

One detail interviewers like

po_lines has its own unit_cost, even though products also has one. Why? Prices change. The order has to remember the price that was agreed on the day you ordered, so the value of a delivery from last month doesn't change when the supplier raises prices today.

5. Read one query line by line: supplier totals

This is the query behind the Supplier totals panel. It has the two things the research said you must be able to explain: a JOIN and a GROUP BY.

{{SQL:SUPPLIER_TOTALS}}

Read it in this order (not top to bottom)

SQL is written select … from … where … group by … order by, but the database runs it roughly as from → where → group by → select → order by. Read it that way:

  1. FROM suppliers s JOIN purchase_orders po ON … — start with suppliers and attach each supplier's orders. s and po are short nicknames (aliases).
  2. JOIN po_lines pl ON pl.po_id = po.po_id — attach each order's lines. Now there is one row per order line, with the supplier and order info next to it.
  3. LEFT JOIN ( … ) rcv — the small query inside the brackets adds up everything received per order line (across all trucks). It's a LEFT join so an order line that received nothing still stays in the result, with null for received. A plain JOIN would silently drop it, and the supplier would look better than it is.
  4. WHERE po.expected_on < current_date — only orders that were already due. Orders still on the truck shouldn't count against a supplier.
  5. GROUP BY s.supplier_id, s.name — fold all the order-line rows into one row per supplier. Every other column must now be a total (sum, count).
  6. SELECT the totals:
    • count(distinct po.po_id): number of orders. Distinct because each order appears once per line; without it, an order with 5 lines would count as 5.
    • sum(pl.qty_ordered) and coalesce(sum(rcv.qty_received), 0): units ordered and received. coalesce turns "nothing" (null) into 0.
    • Fill rate: least(received, ordered) per line, added up, divided by units ordered. least stops 3 extra boxes on one line from hiding 3 missing boxes on another. nullif(…, 0) avoids dividing by zero.
    • sum(rcv.qty_received * pl.unit_cost): dollar value received, using the price on the order.
  7. ORDER BY value_received DESC — biggest supplier first.

A detail worth knowing: the query also selects s.city and s.lead_time_days without listing them in GROUP BY. That's allowed because we group by s.supplier_id, the primary key: Postgres knows each supplier has exactly one city, so there's nothing to add up.

6. The view and its CASE statement

The mismatch table and two of the tiles read from the view po_line_status. It does the "ordered vs. received" comparison once, so every other query can just ask for status = 'short'. The heart of it:

case
  when nothing received and expected_on >= today then 'awaiting'
  when nothing received                         then 'overdue'
  when received < ordered                       then 'short'
  when received > ordered                       then 'over'
  else 'complete'
end as status

CASE checks the conditions top to bottom and uses the first one that's true, like an if / else-if chain. The order matters: "nothing received" has to be checked before "received < ordered", or an overdue line would be called short.

The view is created with (security_invoker = true). That means it runs with the permissions of whoever is asking, so the row-level security rules in section 7 also apply through the view. Without it, a view runs as its owner and could leak rows.

7. Why the AI box uses a read-only user

This is the question the research said you must be able to answer. The short version:

Treat SQL written by an AI like SQL typed by a stranger. It's usually right, but you can't promise it will never write something harmful, especially if someone types a tricky question on purpose. So the database itself must make harm impossible, not the AI's good behavior.

The app stacks several layers. Each one alone would stop most problems; together, a mistake in one is caught by the next. This is called defense in depth.

#LayerWhat it stops
1The app logs in as dashboard_reader, which only has SELECT permissionAny insert, update, delete, drop. The database refuses, whatever the SQL says.
2Before running AI SQL, the app checks the connected user can't writeSomeone pasting the owner's connection string by mistake. The AI box refuses to run.
3A SQL check: one SELECT only, no comments, no data-changing words, no system tables, no risky functionsObvious bad queries, rejected early with a clear message.
4Runs inside a READ ONLY transaction, 3-second timeout, max 200 rows, always rolled backWrites that sneak past layer 3, and slow queries that would tie up the database.
5Row Level Security on every tableIf the schema were ever exposed through Supabase's public API, other roles would see zero rows.
6The query is shown on screenA human can see exactly what ran and judge whether the answer makes sense.

One test deliberately skips layer 3 and sends with gone as (delete from receipts returning *) select * from gone straight to the database. It fails, and the test confirms all 53 receipts are still there.

How the AI part works

  1. Your question goes to the server (never straight from the browser to Claude, so the API key stays secret on the server).
  2. The server sends Claude a short description of the tables and the rules, plus your question.
  3. It uses structured output: the API must answer in a fixed JSON shape: { answerable, sql, explanation }. The app doesn't have to dig SQL out of a paragraph of text.
  4. If answerable is false (for example "what's the weather?"), nothing runs.
  5. Otherwise the SQL goes through layers 2 to 4, and the page shows the explanation, the SQL and the rows.

8. The tests

Run npm test for the 29 unit tests. They don't need a database or an API key. To also run the 16 database tests you need a Postgres you own (for example a local install), and you set TEST_ADMIN_DATABASE_URL. The README has the command.

What makes the database tests worth talking about: they don't just check that the queries run. They rebuild a fresh database from the three SQL files, then work out every dashboard number a second way in plain JavaScript from the same made-up data, and compare. If the SQL and the JavaScript disagree, one of them is wrong. The other database tests try to break the safety layers (write as the reader, skip the SQL check, run a 100-million-row query, connect as the owner, read as an outsider role) and check each attempt fails.

Questions you'll likely get

1. Walk me through your tables. Why are receipts separate from orders?

Header vs. lines; one order can arrive in several deliveries (split shipments); each fact stored once; foreign keys keep it consistent.

2. Explain a query with a JOIN and a GROUP BY.

Use supplier totals (section 5). Mention why it's a LEFT JOIN, why count(distinct), and what GROUP BY does to the rows.

3. What's the difference between INNER JOIN and LEFT JOIN?

Inner keeps only matches; left keeps every row from the left side and fills nulls. Your example: order lines with nothing received.

4. How do you stop the AI from deleting data?

Read-only user first (the database enforces it), then the app's own checks, read-only transaction, timeout and row limit. Say "defense in depth" and "treat AI output as untrusted input".

5. What if the AI writes a query that runs but gives the wrong answer?

That's the real risk, not deletion. The query is shown so a person can check it; the explanation says what it does; for decisions you'd verify with a known report. A next step would be a set of test questions with known answers (an eval).

6. Why Postgres / Supabase?

Real SQL database, free tier, managed hosting, row level security built in, and it's what many startups use.

7. How do you know your numbers are right?

The tests compute each number a second way in JavaScript from the same data and compare. Plus check constraints stop impossible data (negative quantities, more damaged than received).

8. What did Claude Code do, and what did you do?

Be direct: Claude Code wrote the code; the idea and the receiving rules come from your job; you ran it, checked the numbers and can explain it. Only say what you've actually done by then (see section 11). For AI-builder roles this honesty is a plus.

9. What would you build next?

Load receipts from the Receiving Document Reader (the source column is ready); on-time % per supplier; a filter by date range; an eval set for the AI box.

Extra. The chart filters by supplier instantly. Did you write a new query for each click?

No. WEEKLY_UNITS_SQL returns one row per week per supplier (it uses a cross join with suppliers so empty weeks still show). The page adds those rows up in the browser for "all suppliers" or keeps one supplier. That's 72 small rows, so it's cheaper than asking the database again on every click. For millions of rows you'd filter in SQL instead.

10. Practice exercises (hints only)

Try these in the Supabase SQL Editor. Run them as the owner there; that's fine for practice because you're only reading. I've given hints, not answers. When you're stuck, ask me for the next hint first.

Exercise 1. Top 5 most-damaged products

Show product name and total damaged units, highest first, only the top 5.

Hint 1: the view receiving.po_line_status already has product and qty_damaged.
Hint 2: you need sum(...), group by, order by ... desc and limit.
Hint 3: add having sum(qty_damaged) > 0 to hide products that were never damaged.

Exercise 2. Late deliveries per supplier

For each supplier, count orders whose first delivery arrived after expected_on.

Hint 1: first find each order's first delivery date: min(received_on) from receiving.receipts, grouped by po_id.
Hint 2: join that to purchase_orders and then to suppliers.
Hint 3: count(*) filter (where first_received > expected_on) counts only late ones.

Exercise 3. Add a "Damaged %" to each supplier card

Show what share of each supplier's received units arrived damaged.

Hint 1: the supplier cards get their problem counts from SUPPLIER_HEALTH_SQL in src/lib/queries.ts. The view has qty_damaged and qty_received.
Hint 2: the row-to-object code is in src/lib/data.ts (getSupplierHealth), and the card is in src/components/pages/Suppliers.tsx.
Hint 3: you can ask Claude Code to make the change, but first write down what you expect each file change to be, then compare. Run npm test afterwards; the supplier-health test may need the new column too.

Exercise 4. Check the AI (only if you turned it on)

Ask: "Which supplier had the most short lines this month?" Read the SQL it shows. Is "this month" the calendar month or the last 30 days? Is it counting lines or units? Write down whether you agree with it.

This is the skill employers actually want: reading AI output critically, not just accepting it.
